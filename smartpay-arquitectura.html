01 Contexto

¿Qué es SmartPay?

Core de pagos de Asulado (aseguradora). Procesa pólizas, calcula deducciones de ley y libranzas, y dispersa los pagos a participantes y terceros. Corre completamente en AWS.

02 Modelo de negocio

Pólizas y deducciones

SmartPay procesa dos tipos de pólizas y aplica deducciones obligatorias por regulación gubernamental, además de deducciones no obligatorias derivadas de procesos judiciales o libranzas.

Tipos de póliza

⚰️ Sobrevivencia

El causante falleció. Los beneficiarios (cónyuge, hijos, etc.) reciben el pago.

🦽 Invalidez

El causante recibe directamente el pago.

Deducciones de ley

Obligatorias por regulación · aplican según la ley

EPS AFP FSP FSPS

Deducciones no obligatorias

Derivadas de procesos judiciales o libranzas

EMBARGO JUDICIAL EMBARGO CONCILIATORIO LIBRANZAS ACUERDOS DE PAGO APORTES VOLUNTARIOS CAJA DE COMPENSACION
Periodicidad: una solicitud de pago puede ser MENSUAL, QUINCENAL o SEMANAL. Cada deducción / ingreso se evalúa contra una expresión cron por periodo.

04 Dominio · Recepción

Recepción — punto de entrada al core

Java MS Python MS SQS EventBridge Lambda
Clave de lectura: los EventBridge enrutan por el topic en messageAttributes. Recepción publica con topic SOLICITUD_RECIBIDA y el motor cambia el topic al resultado: SOLICITUD_APROBADA, SOLICITUD_RECHAZADA o PENDIENTE_GESTION.
04·b Dominio · Recepción

Motor de reglas xpect

Fachada xpect sobre la librería de Python GX, embebida en un microservicio FastAPI. Reusada en todos los dominios que requieren reglas de negocio. Las reglas se definen en JSON y se evalúan sobre la solicitud entrante.

Stack y patrón

  • Python + FastAPI para mantener el event loop activo.
  • Arquitectura hexagonal · fachada xpect en el dominio.
  • Consumo vía SQS (q-smartpay-motor-recepcion-request-{env}).
  • Publica al bus de EventBridge con un topic según el resultado.
  • Reusable: mismo patrón para otros dominios con motor de reglas.

Tres resultados posibles

✓ APROBADA

Publicada con topic SOLICITUD_APROBADA. EventBridge la enruta al ETL lambda-smartpay-recepcion-pagos.

✕ RECHAZADA

Topic SOLICITUD_RECHAZADA. No avanza dentro del flujo de pagos. Solo se notifica al core.

⏸ PENDIENTE DE GESTIÓN

Topic PENDIENTE_GESTION. Entra a un flujo especial según la regla fallida.

Gestión de pendientes

🔁 Revalidación

El motor re-evalúa la solicitud cuando cambian datos. Al finalizar dispara notificación front por WebSocket.

📤 Solicitud al core

Se pide información adicional o corrección al sistema Salesforce y se queda esperando.

🔓 Levantamiento de control

Operación manual del equipo en frontend. Al confirmar el levantamiento, el motor reevalúa y notifica al front.

04·c Dominio · Recepción

Notificación front por WebSocket

Cuando el motor termina un flujo manual (revalidación o levantamiento de control), debe avisar al usuario en el frontend Next.js sin polling. Se usa API Gateway v2 WebSocket con las sesiones persistidas en DynamoDB.

EventBridge SQS Lambda API GW WS DynamoDB Next.js
Sesión: al hacer $connect el frontend guarda su connectionId en dynamodb-connections-websocket-{env}. La lambda lambda-notificacion-front lee todas las sesiones activas y hace broadcast usando el SDK de API Gateway v2.
05 Dominio · Pagos

Pagos — el “estado real” de cada persona

Microservicio Java Webflux. Es el source of truth de la información de cada persona para SmartPay: deducciones activas, valor de participación en la póliza, rol, cuenta bancaria, datos básicos y de contacto. No tiene lógica de cálculo — es mayoritariamente consulta + algunos endpoints internos.

Java MS Lambda RDS
Patrón clave: Pagos NO tiene endpoints de escritura masiva. Toda inserción/actualización de personas y deducciones llega por la λ recepcion-pagos que actúa como ETL.
Endpoints internos: hay PUT/PATCH puntuales (estado, cuenta bancaria, etc.) y endpoints dedicados a otros dominios — el más usado es /participantes-liquidacion.
06 Dominio · Liquidación

Liquidación — de la consulta cross-schema al plan de pagos

Java MS Lambda EventBridge SQS Step Func DynamoDB
Refactor — beneficios: sin cross-schema; cada solicitud encapsulada en un execution_key en DynamoDB; Step Function maneja el cálculo en una sola transacción; plan de pagos calculado (12 − n + 1) hasta fin de año.
06·b Dominio · Liquidación

Step Function flujo-liquidacion · plan_pagos

Step Function de tipo Express, activada por un pipe de EventBridge desde q-smartpay-flujo-liquidacion-request-{env}. Tiene dos flujos: single y plan_pagos. Aquí nos centramos en plan_pagos, que expande la solicitud a todos los periodos del año restante (12 − n + 1).

Step Func Lambda DynamoDB
Naming: mientras la SF está construyendo el resultado, se conoce internamente como plan_pagos. Cuando liquidación lo lee y lo materializa en sus tablas se conoce como preliquidación. Mismo objeto, distinto nombre según el momento del ciclo.
⚠ Limitación actual: el payload entre estados está topado en 256 KB. En quincenal/semanal con muchas deducciones la SF se rompe (States.DataLimitExceeded). Ver siguiente slide → migración a S3 + Distributed Map.
06·c Liquidación · Migración planeada

Próximo cambio: S3 + JSONL + Distributed Map

Problema actual: al expandir el plan de pagos en periodicidad QUINCENAL o SEMANAL con muchas deducciones, el payload entre estados supera el límite de 256 KB de Step Functions y la ejecución colapsa (States.DataLimitExceeded). El cuello de botella aparece justo en la salida de λ lectura-dynamo hacia el resto de la cadena.
Solución propuesta: λ lectura-dynamo deja de devolver el JSON expandido por el canal de estado. En su lugar hace streaming a S3 en formato JSONL (una línea por periodo + numeroPago). Luego un Distributed Map de Step Functions itera sobre el archivo en S3 y por cada línea ejecuta el sub-flujo de cálculo en paralelo.
Step Func Lambda DynamoDB S3
Por qué Distributed Map: permite ItemReader desde S3 (CSV o JSONL), arranca un sub-workflow por ítem con su propio estado, soporta MaxConcurrency alto y agrega resultados sin que el flujo padre cargue el array completo en memoria.
Beneficios: elimina el States.DataLimitExceeded, baja la latencia E2E al paralelizar los periodos, hace la SF agnóstica de la periodicidad (mensual / quincenal / semanal usan el mismo patrón) y deja un artefacto auditable por ejecución en S3.
06·d Dominio · Liquidación · Cierre

Liquidación parte 2 — cierre de lote, controles y confirmación

Una vez la preliquidación está armada, el lote tiene dos caminos para cerrarse: automático por EventBridge Scheduler (dispara los controles vía el motor de reglas de liquidación) o manual desde el frontend cuando un usuario decide CONFIRMAR LOTE y enviarlo a dispersar.

EventBridge SQS Java MS Python MS RDS Front pipe-a-pipe
Cierre automático: EventBridge Scheduler dispara el cierre por lote. ms-liquidacion envía los participantes al motor de reglas (pipe-a-pipe), recibe los PENDIENTES, los reubica en un lote falso temporal, recalcula deducciones y los devuelve al lote real corregidos.
Confirmar lote (manual): proceso 100% disparado por el usuario desde el frontend. Solo si el lote terminó APROBADO se puede confirmar. La confirmación emite un mensaje directo (sin EventBridge) a la cola del MS Dispersión.
06·e Dominio · Liquidación · Análisis del repositorio

ms-liquidacion — entradas, salidas y adapters reales

Mapa completo extraído del repositorio: 10 tipos de evento SQS, ~30 endpoints HTTP, 6 productores SQS (incluido el mensaje directo a Dispersión) y callback de Step Functions vía sendTaskSuccess/Failure.

SQS Java MS Front HTTP Step Func DynamoDB RDS
Eventos con taskToken: INICIAR_ACTUALIZACION_PLAN_PAGOS y ACTUALIZAR_PLAN_PAGOS traen un taskToken en payload — son los que vienen de una Step Function esperando callback. Los handlers de PaymentPlanHandler / PreliquidationPlanHandler reciben listas de participantIds / paymentRequestId.
06·f Dominio · Liquidación · Integraciones

ms-liquidacion · servicios externos — Mulesoft (Payroll Download) y APIs internas

ms-liquidacion también integra con Mulesoft con OAuth2 client_credentials + bearer cacheado, pero el caso de uso es distinto al de Dispersión: aquí se usa para descarga de nómina (PayrollDownloadIntegrationAdapter → liquidationPaymentsPath). El resto son llamados HTTP a las APIs internas de Asulado, a ms-pagos (3 WebClients distintos), a ms-maestro y a la lambda de parámetros.

Java MS OAuth / Mulesoft Lambda (API GW) API privada Asulado
07 Dominio · Dispersión

Dispersión — del lote confirmado a contabilidad

Dispersión recibe el lote confirmado, consulta a Liquidación qué tipos de lote debe materializar (ESTÁNDAR / ESPECIAL / ambos) y crea un lote por cada tipo. Luego una lambda ETL puebla esos lotes con el detalle del lote original y, en cadena (pipe-a-pipe), otra lambda lleva la información a Contabilidad.

Java MS Lambda SQS RDS pipe-a-pipe
Tipo de lote: Dispersión consulta primero GET /tipo-lote y, según si el lote es ESTÁNDAR / ESPECIAL / ambos, crea uno o dos lotes de dispersión.
▪ ESTÁNDAR = participantes + terceros no especiales (libranzas, acuerdos, aportes).
▪ ESPECIAL = terceros de embargos + seguridad social + caja de compensación.
Cadena de lambdas pipe-a-pipe: ms-dispersion → λ liquidacion-dispersion → λ liquidacion-contabilidad. Toda la cadena va por pipes directos entre colas — deuda técnica visible: si se requiere observabilidad de dominios o nuevos consumidores, falta migrar al patrón de fanout con bus bus-smartpay-{env}.
07·b Dominio · Dispersión · Parte 2

Dispersión parte 2 — motor de reglas y notificación al frontend

Una vez los lotes están creados, Dispersión ejecuta controles contra el motor de reglas de dispersión (pipe-a-pipe). Los registros que el motor marca como PENDIENTES vuelven por otra cola para gestión, y los cambios de estado se notifican al frontend Next.js por WebSocket. El cierre puede dispararse de forma automática (EventBridge Scheduler) o manual (frontend).

EventBridge SQS Java MS Python MS Lambda API GW WS DynamoDB Next.js pipe-a-pipe
Motor pipe-a-pipe: dos eventos viajan a la misma cola motor-result-queue — APLICAR_CONTROLES_LOTE (lote completo) y VERIFICAR_CONTROLES_REGISTRO_PERSONA (un registro específico, destination=MOTOR_DISPERSION). El motor responde por la cola MOVER_REGISTROS_LOTE con los pendientes.
07·c Dominio · Dispersión · Integraciones

Dispersión · servicios externos — Mulesoft (SAP) y APIs internas

Dispersión llama varios servicios HTTP externos. El más crítico es Mulesoft con OAuth2 y bearer cacheado, que entrega la transacción de dispersión bancaria a la API de SAP. El resto son endpoints HTTP a la API privada de Asulado (api-privada.pruebas.asulado.com.co/smartpay) y a la lambda de parámetros (API Gateway).

Java MS OAuth / Mulesoft SAP Lambda (API GW) API privada Asulado
08 Dominio · Novedades

Novedades — alteraciones de pagos y deducciones

Novedades es la segunda puerta de entrada de SmartPay. Recibe alteraciones que afectan los pagos de una persona — por ejemplo, una nueva libranza, un embargo judicial o un cambio de datos bancarios. Todo el dominio se comunica con fan-out vía EventBridge + SQS, salvo el tramo hacia el motor de reglas que aún es pipe-a-pipe.

Java MS Python MS EventBridge SQS Step Func Lambda pipe-a-pipe
Patrón general: todo el dominio de Novedades usa fan-out con EventBridge + SQS, excepto el tramo ms-novedades → motor de reglas que aún es pipe-a-pipe. Las novedades de tipo DATOS BÁSICOS y DATOS BANCARIOS siguen el mismo esquema general pero no requieren la consulta de capacidad de endeudamiento.
08·b Dominio · Novedades · Plan de pagos

Novedades · actualización del plan de pagos — callback a Liquidación

Cuando una novedad de DEDUCCION es aprobada, la State Machine de Novedades dispara la lambda novedades-deducciones (REGISTRO / ACTUALIZACION / RETIRO según el caso). Para que el cambio se vea reflejado en los pagos futuros de la persona, la SF llama a Liquidación con waitForTaskToken para que actualice el plan de pagos: Liquidación reusa la misma Step Function del plan_pagos pero con tipo ACTUALIZACION, identifica el período y número de pago a partir del cual aplica, CANCELA los registros viejos y CREA los nuevos.

Step Func Lambda SQS Java MS DynamoDB
Patrón clave: la SF Novedades usa waitForTaskToken para "pausarse" mientras Liquidación hace el trabajo pesado de cancelar y crear registros en el plan de pagos. Cuando liquidación termina llama sendTaskSuccess y la SF retoma — esto es lo mismo que ya vimos en StartUpdatePaymentPlanHandler / UpdatePaymentPlanHandler en la slide del análisis de ms-liquidacion. La actualización es una operación dual: CANCELAR viejos + CREAR nuevos.
09 Dominio · Contabilidad

Contabilidad — integración con SAP

Dominio del extremo del flujo. Recibe los eventos de Dispersión (CUENTAS_POR_CANCELAR) y se integra con SAP a través de Mulesoft para registrar las cuentas por cobrar (CxP) y realizar los cruces de débitos vs. créditos. El detalle interno queda fuera de alcance de esta presentación.

SQS Lambda Java MS Mulesoft SAP
Alcance: el detalle interno de Contabilidad queda fuera de esta presentación. Lo que importa de cara al equipo es que es el receptor final de los movimientos contables y el que integra con SAP (vía Mulesoft) para registrar CxP y validar los cruces débito/crédito.

10·a Errores comunes · Frases del equipo

"Se dañó la 18001" — dos cosas distintas según el contexto

En el equipo, decir "se dañó la 18001" puede significar dos cosas distintas según con quién hables. En realidad 18001 alude al endpoint /hv de ms-pagos (hoja de vida de un participante) o a la ETL liquidacion-recepcion que pobla el histórico en Recepción. Conviene tener clara la diferencia para diagnosticar más rápido.

Cómo desambiguar al diagnosticar: si el problema reportado es que el lote actual o el detalle de un participante se ve incompleto / sin deducciones, normalmente es la interpretación 1 (/hv). Si el problema es que el histórico no aparece o no se actualiza tras un cierre, normalmente es la interpretación 2 (λ liquidacion-recepcion).
10·b Errores comunes · Frases del equipo

"Liquidación no liquida" — diagnóstico por tablas

Cuando operación reporta que "liquidación no liquida" el problema puede estar en distintos puntos del flujo. La forma rápida de aislarlo es revisar qué tablas quedaron pobladas en el schema de liquidación y deducir en qué evento se rompió.

Atajo de diagnóstico: con un solo SELECT en el schema esquema_liquidacion sobre las tres tablas base (tliq_persona, tliq_solicitud_pago, tliq_info_bancaria) y sobre las tablas de preliquidación se aísla en segundos cuál es el evento que falló.
10·c Errores comunes · Frases del equipo

"No llegan las notificaciones al frontend" — diagnóstico por capa

La cadena de notificación al frontend tiene varios eslabones (productor → EventBridge → cola → lambda → DynamoDB → API Gateway WebSocket → Next.js). El truco es localizar en qué eslabón se cortó recorriendo la cadena de inicio a fin.

Atajo de diagnóstico: abrir CloudWatch en paralelo y mirar tres métricas en orden — (1) ApproximateNumberOfMessagesVisible de la cola, (2) Errors de la lambda, (3) ItemCount de la tabla DynamoDB de sesiones. En menos de 30 segundos se localiza el eslabón roto.
